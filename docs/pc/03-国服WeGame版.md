# 国服 WeGame 版实测

另一个客户端实例：国服 WeGame 版，安装目录 `E:\[3]Nikke\NIKKEG`，`core` 修订号 569366。

与 [01-实测.md](01-实测.md) 的国际服**不是同一个包**，两边的体量、键数不能混用。容器格式完全一致，取件算法通用；差异只在数据本身。

写这份是为了记录三点：国服的桶体量、国服 `store.cdb` 存在空隙、国服 `en`/`ko` 比国际服更空。

## 1. 识别

| 项 | 值 | 取法 |
| :--- | :--- | :--- |
| 安装目录 | `E:\[3]Nikke\NIKKEG` | 启动器目录，含 `Launcher/` `NIKKE/game/` `Unity/` |
| 资源根 | `<安装目录>/Unity/com_proximabeta_NIKKE/com.shiftup.patch` | 与 01-实测 结论一致：由启动器决定，不在安装目录的 `game` 下 |
| 版本标识 | `coreRevision 569366` | `.patch_state.json` |
| 引擎 | `UnityFS` 5.x，`2021.3.56f2` 族 | bundle 头部版本字符串 |

`.patch_state.json` 各桶修订号独立：

| 桶 | revision |
| :--- | --: |
| core | 569366 |
| dp | 571461 |
| fd | 563415 |
| en / ja / ko | 570215 |
| saus | 570617 |

`existingGroups` 只有 6 项，没有 `RequiredQuality_Texture_SD`。这与下文 §4 的缺口直接对应。

## 2. 七桶体量

与 01-实测 的国际服对照。两列都是实测字节，来源不同版本，**不是同一份数据的两种量法**。

| 桶 | `store.cdb` | idx 条数 | catalog 键数 | catalog 块数 | 国际服键数（01-实测） |
| :--- | --: | --: | --: | --: | --: |
| core | 6,929,202,210 | 256,203 | 26,758 | 274,433 | 27,905 |
| dp | 13,217,314,580 | 239,955 | 13,802 | 284,877 | 14,749 |
| fd | 2,099,890,295 | 45,745 | 492 | 45,745 | 517 |
| ja | 4,135,549,604 | 57,238 | 2,107 | 57,238 | 2,190 |
| en | 无 | 0 | 2,107 | 56,312 | 2,190 |
| ko | 无 | 0 | 2,107 | 55,442 | 2,190 |
| saus | 19,706,390 | 279 | 1 | 279 | 1 |

`saus` 的 `store.cdb` 字节与国际服逐字节相同（19,706,390），说明这一桶两服同包。

国服各桶键数普遍比国际服少 3% 左右，`dp` 少 947 个键。同一份文档里的族名结论仍然适用，只是可用资源少一批。

## 3. `en` / `ko` 比国际服更空

01-实测 记的是「`en` / `ko` 没有 `store.cdb`，内容全走 raw 层」。国服这两桶连 raw 层都没有：

```
en/
├── catalog.ndb          4,594,416 B
└── catalog.ndb.nds             96 B
```

只有两个文件。清单完整（2,107 键 / 56,312 块登记在案），块数据一个都没落盘。对这两个桶取任何键都会因缺 `store.cdb` 失败，这是安装状态而非解析问题。

`fd` / `ja` / `saus` 三个桶则同时有 `store.cdb` 与 `raw/`，`raw/` 下 2 个文件（`.db` + `.nds`），`saus/raw/` 下有 192 个（`.lsc` `.mp4` `.cat`）。

## 4. `store.cdb` 有空隙

01-实测 对国际服的结论是「`256 + Σ(idx.size)` 五桶闭合、零间隙」。国服不闭合，除 `saus` 外四桶都有间隙：

判定方法：按 `pos` 排序后检查相邻块是否首尾相接。`prev_end = max(prev_end, pos + comp)`，`pos > prev_end` 记为间隙，`pos < prev_end` 记为重叠。

| 桶 | 块数 | `256 + Σ(comp)` | 文件字节 | 差 | 间隙数 | 间隙字节 | 重叠 |
| :--- | --: | --: | --: | --: | --: | --: | --: |
| core | 256,203 | 6,877,399,344 | 6,929,202,210 | 51,802,866 | 4,861 | 51,802,866 | 0 |
| dp | 239,955 | 13,209,598,671 | 13,217,314,580 | 7,715,909 | 336 | 7,715,909 | 0 |
| fd | 45,745 | 2,086,140,491 | 2,099,890,295 | 13,749,804 | 1,036 | 13,749,804 | 0 |
| ja | 57,238 | 4,133,554,499 | 4,135,549,604 | 1,995,105 | 44 | 1,995,105 | 0 |
| saus | 279 | 19,706,390 | 19,706,390 | 0 | 0 | 0 | 0 |

四桶空隙合计 75,263,684 B（约 71.8 MiB），相对 26 GiB 可忽略。重叠恒为 0，说明块之间没有共享区，一个块只对应一个位置。

首块 `pos` 全为 256，与全局头长度一致。

这条差异不改变取件算法——仍然只信 idx——但它说明「文件为零间隙紧密排列」不是跨客户端的通用性质。做偏移反推类校验时不能把它当断言。

## 5. 缺块全部落在 `(sd)`

对全量键逐块比对 idx 覆盖，缺口不是散点而是整族：

| 桶 | 总块 | idx 覆盖 | 覆盖率 | 缺键 | 缺口归属 |
| :--- | --: | --: | --: | --: | :--- |
| core | 274,433 | 256,203 | 93.4% | 418 | `spotmonster(sd)` 239 / `spotbackground(sd)` 174 / `icon-spriteatlas(sd)` 3 / `uipatch(sd)` 2 |
| dp | 284,877 | 239,955 | 84.2% | 4,900 | `RequiredQuality_Texture_SD` 2,638 + `RequiredQuality_Spine_SD` 2,262 |
| fd / ja / saus | — | — | 100% | 0 | — |

缺键合计 5,318，与两个 SD 分组之和加 core 零头精确相等。**判定为安装时未下载低清包**，与 01-实测 §6 对国际服的定论方向一致：查不到的块没有磁盘位置，只能靠游戏内按需下载补。

程序上要先查覆盖再取件。缺块时抛明确原因，不要让它走到 zstd 解压再报一个无关的错。

## 6. 取件实测

四个校验点，全部通过：

| 动作 | 结果 |
| :--- | :--- |
| idx 随机抽 15 条按 `pos`/`comp` 直读解压 | 15/15 成功，首条解出 `UnityFS` |
| `icons-char-full(hd)_assets_c810_00_...bundle` | 20 块拼出 4,217,552 B，UnityPy 取到 2048×2048 RGBA 贴图 |
| `spinecombatcharactergroup(hd)_assets_spine/combat/c810/00/aim_hd_...bundle` | 38 块，`.atlas` + `.skel` + 贴图齐全，`skel` 版本串 `4.1.20` |
| `spinestandingcharactergroup(hd)_assets_spine/standing/c223/00_hd_...bundle` | 139 块，12,658,240 B，双 2048×2048 图集 |

`spinecombatcharactergroup` 与 `spinestandingcharactergroup` 的键路径、族名、`(hd)`/`(sd)` 标记与安卓逐字相同，安卓侧的键解析规则直接可用。

## 7. 复现

只读客户端，不写入。解密结果缓存在工具目录，删掉可重建。

```bash
python cli.py pc-scan "E:/[3]Nikke/NIKKEG"
python cli.py pc-find "E:/[3]Nikke/NIKKEG" "standing/c223" --bucket dp
python cli.py pc-get  "E:/[3]Nikke/NIKKEG" dp "<完整键>" -o out/x.bundle --png
```

`.patch_state.json` 的 `revision` 与安卓 `versionName` 的对应关系仍未验证。两边没有共同字段，只能靠键数或文件指纹人工对齐。
