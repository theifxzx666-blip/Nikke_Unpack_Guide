# 采集一个资源，要走哪几步

这份文档回答一个问题：手里只有一个线索（活动名、角色名，或者一句「我要这个活动的立绘」），
怎么在半小时内稳定拿到文件，而不是在几十 GB 的客户端里瞎翻。

只讲怎么用，不讲字节结构。容器原理见 [common/容器-国际服.md](common/容器-国际服.md)，
国服按名检索的可行性见 [06-国服按名检索方案.md](06-国服按名检索方案.md)。

---

## 一、这套流程到底在做什么

拆包这件事，真正耗时间的不是「解开文件」，而是三件反复发生的事：

1. **不知道资源在哪个服**，于是在没有这个活动的客户端上白找一遍；
2. **不知道该搜什么名字**，于是把成千上万个包逐个打开看；
3. **每个文件都重新起一次程序**，于是取 100 个文件和取 1 个文件的单价一样贵。

对应的三个动作是：先探路、再列清单、最后一次性批量搬。三件事都不做，就会变成
「翻一小时，找到 3 个文件，导出花 5 分钟」。

一次完整的采集，从线索到成品是五步：

```
定位（在哪个服、有多少）
  → 列清单（把名字变成键）
  → 预检（哪些本地真有）
  → 批量取件（一个进程搬完）
  → 归档（按来源命名，下次能复用）
```

正常情况下一轮 30 秒到 2 分钟；首次使用因为要解密清单、建索引，会多花几分钟，
这部分是一次性成本，之后一直有效。

## 二、第 0 步：先确认资源在哪个服

**做什么**：给一个关键词，同时问国际服和国服「你有没有」。

```bash
python tools/nk.py locate marian \
  --intl-root "D:/PanDownload/Nikke_local/NIKKEG" \
  --cn-root "E:/WeGameApps/rail_apps/胜利女神：新的希望(2002017)/nikke_Data"
```

**为什么**：这一步是补上去的。之前找了半天 MARIA-n 的立绘，最后发现国服清单里
只有 9 条同名音频（四周年小游戏音效），UI、剧情 CG、场景 Spine 一条都没有——
不是工具失灵，是这个活动国服没上。没有这一步，工具越好，空转越快。

**怎么看结果**：

```
== 国际服  命中 198  core:89 dp:109
    构成 scenariobackground:98 eventui-marian:42 audiogroupui:36 spineeventgame-fortheking:8
== 国服   命中 9  包 9  本地已有 9
    构成 event:5 sfx:4
>> 建议：both  两服都有：国际服 198 条 / 国服 9 条……
```

两个数字要连起来看，不能只看有没有：

| 现象 | 含义 | 下一步 |
| :-- | :-- | :-- |
| 只有一侧有 | 另一侧没上这个活动 | 直接去有的一侧 |
| 两侧都有，数量接近 | 内容基本同源 | 按需要的语种挑 |
| 两侧都有，但差一个数量级 | 少的那侧大概只有音频/占位 | 看 `构成` 和样例，别急着开跑 |
| 两侧都是 0 | 关键词拼错，或版本还没上 | 换英文名、换活动 ex 名再试 |

**耗时**：0.4 秒（国际服七桶目录已解密、国服清单已摊平的前提下）。
首次会慢一些：国际服七桶解密约 2 秒，国服 43 MB 清单解析约 1 秒，之后都走缓存。

**只记得一个服也行**：少给一个路径，它就报「未检查」，不会假装查过。
路径写错会明确报「找不到国服 catalog.json」，而不是静默返回 0 条。

## 三、第 1 步：把关键词变成键表

**做什么**：在指定服里按名字搜，把命中的条目写成一份文本清单。

```bash
python tools/nk.py find "marian" --all --keys keys.txt
```

**为什么**：后面的取件命令要的是「键」——带路径和哈希的完整标识，不是「marian」这种
人能读的名字。这一步就是翻译。顺带解决一个问题：同一个活动的资源散在不同桶里
（`core` 放 UI 和音频，`dp` 放剧情背景，`fd/en/ja/ko` 放文本），只查一个桶会漏，
而且漏了不报错。

**注意事项**：

- 命中多个桶时会拆成 `keys_core.txt`、`keys_dp.txt`。因为取件命令一次只认一个桶，
  混在一起的键表会让另一桶的条目全部报找不到。
- `--all` 是「查全部七个桶」。不加就只查默认的 `core`，多数情况不够。
- 已经有解密好的目录时加 `--cat <目录>`，省掉重复解密。

**耗时**：198 个键 82 毫秒。

---

## 四、第 2 步：先问「哪些本地真的有」

**做什么**：不用单独执行，取件命令默认会先跑一遍预检。

```
预检: 键 109  可拉 55  物理缺失 54  清单无此键 0
  缺 21 块  scenariobackground(sd)_assets_eventscene_marian_02_2_…
```

**为什么**：清单是「官方有这个资源」，不等于「你机器上有」。游戏按画质和进度按需下载，
清单里有、本地没落盘的键会取件失败。不预检就要等跑完才看见一堆报错，还分不清是
版本不对、键写错、还是本来就没下载。

预检把结果分三类，判据和真正取件时是同一条：

| 判定 | 含义 | 处理 |
| :-- | :-- | :-- |
| 可拉 | 数据块都在 | 正常取 |
| 物理缺失 | 清单有，本地没下载 | 进游戏触发一次下载，或跳过 |
| 清单无此键 | 名字对不上 | 版本变了，重查清单 |

**耗时**：109 个键几十毫秒。

**两个开关**：`--skip-missing` 只拉能拉的（推荐，实测比带失败跑还快 1.2 秒，
因为失败也要付一次取件的钱）；`--no-precheck` 关掉预检，回到老行为。

## 五、第 3 步：一次性搬完

**做什么**：一个进程吃掉整份键表，取件并直接导出成图片、音频、文本。

```bash
python tools/nk.py batch keys_core.txt --bucket core -o out/core --jobs 4 --skip-missing
python tools/nk.py batch keys_dp.txt   --bucket dp   -o out/dp   --jobs 4 --skip-missing
```

**为什么不能写 for 循环**：单个文件 2 秒左右，其中 1.75 秒是启动解释器和加载解析库，
真正读数据只占几百毫秒。逐件起进程等于每件都重付一次这笔固定开销。一个进程连续处理，
这笔钱只付一次。实测：

| 做法 | 取 89 个文件 | 平均每件 |
| :-- | --: | --: |
| 一件一条命令 | 约 3 分钟 | 2.05 秒 |
| 一个进程批量 | **18 秒** | 0.20 秒 |

`--jobs 4` 是四进程并行。实测四进程是饱和点，八进程只再快 8%，再多是浪费。

**导出会慢多少**：`batch` 是取件 + 导出一步到位。纯取件 100 件约 5 秒；
带导出（写 PNG、拆 Spine、转音频）会到几十秒，因为主要时间花在解码和写盘上。
需要判断「值不值得拉」时，可以先只取件看体积，再决定导不导。

**只导出需要的类型**：加 `--only` 给一个关键词白名单，名字不命中的对象只统计不落盘。

```bash
python tools/nk.py batch keys.txt --scene cn-pc -o out/ --only "trueflavor,crust,bready"
```

为什么需要这个：活动 UI 往往和公共元素（`ele_*`、`fx_*`、`common_*`）打进同一张图集，
整包导出必然带出别的活动的东西。实测 TRUE FLAVOR 的 22 个包里共 23,578 个对象，
属于该活动的只有 508 个；不加白名单会写出 381 张图、38 MB，加了只剩 201 张、19 MB，
而且取件时间从 7.0 秒降到 4.4 秒——少写的那部分也要花时间。

代价是要自己列关键词。稳妥做法是先用活动名，跑一遍看 `kept / skipped`，
再从产物里补角色名（如 `crust`、`bready`）。

**国服的批量走同一条命令**，只是键换成对象名、预检换成查索引：

```bash
python tools/nk.py locate "marian" --cn-root "E:/.../nikke_Data" --cn-keys cn_keys.txt
python tools/nk.py batch cn_keys.txt --scene cn-pc --root "<cache 根>" -o out/ --jobs 4 --skip-missing
```

实测 200 个对象名，11.0 秒（55 毫秒一件），产出 851 个文件 / 150 MB；
同样的活写成 for 循环逐件起进程要 200 × 2.3 秒 ≈ 7.7 分钟，差 42 倍。

国服的键表有两个额外讲究，国际服不涉及：

- **一行一个对象名，不带扩展名**（`sfx_scn_mariancannon`，不是 `xxx.bundle`）；
- **注释要写成 `# 空格`**。国服真实存在 `##_board_touchtext` 这种名字，
  也有以空格开头的 ` sound_hacking_active`，按「`#` 即注释 + 每行 strip」处理会被静默吞掉。
  工具已经按这个规则读，但自己手写键表时容易踩。

## 六、第 4 步：归档，让下一次不用重来

命名和目录不用每次重新想，照这三条：

1. **目录按「场景_日期/桶」**，例如 `国际服PC_20261103/core`。换版本时另起一个，不要覆盖。
2. **键表一起存**。`keys_core.txt` 和产物放同层，下次版更直接重跑，不用重新搜。
3. **失败清单单独记**。预检报出的「物理缺失」写进一个 `missing.txt`，下次进游戏下载完只补这批。

这一步花不了一分钟，但决定了下次是「重跑一条命令」还是「重新摸一遍」。

## 七、三种起点，对应三条路

| 你手里有什么 | 第一条命令 | 之后 |
| :-- | :-- | :-- |
| 只有活动名/角色名 | `locate <名字>` | 确认服 → `find --all --keys` |
| 知道资源类型，比如「只要活动 UI」 | `find <活动名> --all` | 看键前缀，只把 `eventui-*` 的行留给 batch |
| 有确切键 | 直接 `pull <键>` | 单件；多件凑成键表走 `batch` |

第三种最容易：`pull` 一条命令完成取件加导出，适合验证「这个键到底是不是我要的那张图」。

## 八、怎么复用

这套东西的价值不在跑一次，在于下次遇到新活动时能直接套。四种用法：

**一、当技能用。** 整个目录就是一份技能，`SKILL.md` 里写了触发条件和流程。
不装到用户目录也能用，需要时在项目里指定路径即可。若确实要装：

```bash
# 只做软链，不复制。注意别把大文件一起链进去
mklink /J "%USERPROFILE%\.workbuddy\skills\nikke-unpack" "<本仓库克隆路径>"
```

**二、当命令用。** 把解释器和仓库路径固化成两个变量，每次只需改关键词：

```bash
set PY=<装了 UnityPy 的解释器>\Scripts\python.exe
set NK=<本仓库克隆路径>\tools\nk.py
%PY% %NK% locate <名字> --intl-root "D:/.../NIKKEG"
```

解释器必须是装了 UnityPy 的那个。用错会直接提示「缺少依赖」并给出完整可复制的命令，
不会刷一屏导入错误。

**三、当模板用。** 键表是纯文本，可以进版本库。把「MARIA-n 需要哪些包」这样的结论
存成 `keys_*.txt`，下次版更直接跑 `batch`，跳过定位和检索两步。

**四、当回归基线用。** 每次客户端更新后跑一次 `locate`，对比命中总数。
数字突然掉一半，说明命名规则改了；数字暴涨，说明新版本加了资源。比人工翻目录靠谱。

## 九、拿不到的情况，以及为什么

诚实列出来，免得下次又白花时间：

| 情况 | 表现 | 原因 |
| :-- | :-- | :-- |
| SD 画质变体缺失 | 预检报「物理缺失」，同一资源 HD 版正常 | 游戏只下载当前画质用到的块，SD 是可选包 |
| 国服搜不到角色立绘 | `locate` 国服命中只有音频 | 国服图像资源多打成图集大包，命名不含角色名，按名搜天然搜不到 |
| 活动在某服完全没有 | 该侧命中 0 | 版本不同步，不是工具问题 |
| 安卓读不到数据目录 | adb 报权限错误 | 国产 ROM 需要 `su` 拷到 `/sdcard` 并 `chmod 666` |

关于国服按名检索：能做，但覆盖面取决于命名习惯。音频、活动、玩法类命中率接近 100%，
图像类偏低。详细可行性数据在 [06-国服按名检索方案.md](06-国服按名检索方案.md)。

## 十、一页速查

```bash
# 0 定位
nk locate <名字> --intl-root <国际服根> --cn-root <国服根>
# 1 列清单
nk find <名字> --all --keys keys.txt                  # 国际服：键
nk locate <名字> --cn-root <国服根> --cn-keys cn.txt   # 国服：对象名
# 2+3 预检 + 批量
nk batch keys_core.txt --bucket core -o out/core --jobs 4 --skip-missing
nk batch cn.txt --scene cn-pc --root <cache 根> -o out/ --jobs 4 --skip-missing
# 单件验证
nk pull <完整键> -o out/
```

| 指标 | 数值 |
| :-- | :-- |
| 定位一次 | 0.4 秒 |
| 检索 198 个键 | 0.08 秒 |
| 国际服取件 + 导出 89 件 | 18 秒 |
| 国服取件 + 导出 200 件 | 11 秒 |
| 一轮完整采集（已知活动名） | 30 秒 ~ 2 分钟 |
| 首次额外成本 | 清单解密 2 秒；国服建索引约 4 分钟（一次） |

对照旧做法：同样是 MARIA-n 这批资源，逐个打开 117 个场景包找线索约 11 分钟，
再逐件导出 144 个文件约 5 分钟，合计 16 分钟以上，且中途出错要重来。
现在约 30 秒，且每一步都有可核对的分项数字。
