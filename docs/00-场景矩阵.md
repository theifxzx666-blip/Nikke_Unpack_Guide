# 四场景矩阵

四个场景不是四套方案，是 **两个正交维度** 的组合：

- **容器形态**决定清单与数据体格式（硬分叉），走错一步后面全错。
- **端**（PC / 安卓）只决定 **字节怎么搬**，容器之后的解析完全一致。

容器形态**与服名不是一一对应**，这是最容易判错的地方：

| 容器形态 | 清单 | 数据体 | 谁在用 |
| :--- | :--- | :--- | :--- |
| **七桶** | `<桶>/catalog.ndb`（`NKDB`） | `<桶>/chunk/store.cdb` + `.idx`（`CIDX`） | 国际服 PC / 安卓；**国服也存在这种形态**（见 [cn-pc/01-实测](cn-pc/01-实测.md)） |
| **缓存** | `com.unity.addressables/*.json` | `cache/<hexA>/<hexB>/__data` | 国服 WeGame 版；国服安卓 |

```
                七桶形态                        缓存形态
PC      NKDB + store.cdb，本地直读      Addressables JSON + UnityCache，本地直读
安卓    NKDB + store.cdb，adb dd 定点读 Addressables JSON + UnityCache，adb pull
```

**先判容器，再判端。** 判错的代价不对称：把缓存形态当七桶，会去 `store.cdb` 里找一个根本不存在的文件，卡在第一步且毫无提示；反过来同理。

服的差异体现在**内容**上：键数少 3% 左右、文本表不同语言、部分资源未下发。容器层面的结论可以跨服复用。

## 一、判定表（动手前 30 秒）

先看有没有七桶目录，再决定走哪套。

| 判据 | 七桶形态 | 缓存形态 |
| :--- | :--- | :--- |
| 目录特征 | 有 `com.shiftup.patch/{core,dp,fd,en,ja,ko,saus}` | 有 `runtime_data/cache` 或 `UnityCache/Shared` |
| 清单 | `<桶>/catalog.ndb`，魔数 `NKDB` | `com.unity.addressables/*.json`，明文 |
| 数据体 | `<桶>/chunk/store.cdb` + `store.cdb.idx`（`CIDX`） | `cache/<32hexA>/<32hexB>/__data` |
| 文本表 | `saus/raw/<16B hash hex>.lsc`，**NKDB 加密** | `saus/saus/lss/*.lss`，**明文 SQLite** |
| 包名（安卓） | `com.proximabeta.nikke` | `com.tencent.nikke` |
| 版本标识 | 安卓 `dumpsys package` 可读 | 同左；PC 只有文件指纹 |

**一条命令自查**（不用记表）：

```bash
python tools/nk.py doctor --scene intl-pc --root "D:/.../NIKKEG"      # 七桶形态
python tools/nk.py doctor --scene cn-pc   --root "E:/.../runtime_data/cache"   # 缓存形态
```

场景名里的 `intl` / `cn` 指的是 **容器族**，不是服名。国服若装了七桶形态的客户端，按 `intl-*` 跑。

## 三、四个场景的链路

### A 国际服 PC

```
七桶 catalog.ndb → NKDB 解密（AES-128-OFB，密钥在偏移 8）→ SQLite
  → files_chunktype 查 file_id → chunk_file_map 按 file_offset 排序
  → chunks 取 hash / original_size → store.cdb.idx（CIDX）查 pos
  → 本地 seek+read → zstd 解压 → 断言 len==original_size → 按序拼接
  → UnityFS → UnityPy → PNG / WAV / TSV
```

### B 国际服安卓（ADB）

```
① 清单与索引 pull 到本地：catalog.ndb + store.cdb.idx（各几 MB）
② 解密 + 查表同上，得到 [(hash, pos, size)]
③ 按 pos 排序，间隔离散则分批，每批一次：
   adb exec-out "dd if=<store> bs=4096 skip=<pos> count=<size> iflag=skip_bytes,count_bytes"
④ 校验 len(stdout)==size，zstd 解压，按 file_offset 拼接
⑤ UnityPy 导出
```

三条硬约束（违反不报错，只出错东西）：

1. 必须 `exec-out`，`adb shell` 会把 dd 统计行混进 stdout。
2. 必须 `iflag=skip_bytes,count_bytes`，toybox dd 默认按记录数算。
3. 拼装必须按 `file_offset`，不是按物理偏移排序。

### C 国服 PC

```
com.unity.addressables/*.json → m_InternalIds 取 bundle 名
  → 末尾 32 hex 即包内 `<hash>.bundle` 对象名
  → 在 cache 里按对象名反查 → cache/<hashA>/<hashB>/__data
  → 读前 4 字节判定：UnityFS 直读 / NKAB 过 NAU
  → UnityPy 导出
```

国服没有 `catalog.ndb`，**也没有可用的 `catalog JSON → cache 路径` 映射**：缓存目录名与 bundle 名无确定关系，md5 的各种变体实测全部不命中。定位只能靠内容。

### D 国服安卓（ADB）

```
① adb pull /files/com.unity.addressables/*.json 取清单
② adb pull /files/saus/saus/lss/*.lss 取文本表（明文 SQLite，直接可查）
③ 资源包按 __data 拉取（单文件 pull，不需要 dd 切块）
④ 头部判定 UnityFS / NKAB，NKAB 走 NAU
⑤ UnityPy 导出
```

## 四、四处真差异（不是参数不同，是机制不同）

| # | 项 | 七桶形态 | 缓存形态 |
| :-: | :--- | :--- | :--- |
| 1 | 清单 | 自研 `NKDB`（AES-128-OFB，头内带密钥） | Unity Addressables 明文 JSON |
| 2 | 数据体组织 | `store.cdb` + `CIDX` 索引，块级 zstd | Unity Cache 目录树，整包文件 |
| 3 | 文本表 | `.lsc`，NKDB 加密 | `.lss`，明文 SQLite |
| 4 | 取件粒度 | 块（要 dd 拼装、要校验连续性） | 整文件（pull 即可） |

**第 4 条决定工具形态**：七桶必须写块级取件与拼装校验；缓存形态只要定位到文件就能拿，难点全在「定位」。

同一个资源类，四个场景的可用性和规格并不一致，按需查：

| 类 | 国际服 PC | 国际服安卓 | 国服 PC | 国服安卓 |

## 六、最容易踩的五个坑

1. **PC 资源根不在安装目录**。国际服由启动器指定，`Unity/com_proximabeta_NIKKE` 才是；`game` 目录只有 exe。最省事的定位法是读 `Player.log` 里的 `GetGameResourcePath`。
2. **`.idx` 查不到就是物理不存在**。国际服 `256 + Σ(idx.size) == store.cdb 大小`，五桶闭合，别用 `pak_offset` 反推。但这条**不是通用性质**：国服四桶实测有 71.8 MiB 空隙，不能当断言用。
3. **国服的 NKAB 不一定在缓存里**。本机 WeGame 版 22,210 个缓存条目全是明文 `UnityFS`；NAU 只在处理下载流密文时用。**先读 4 字节再决定要不要解密**，不要预设。
4. **SD 分组要整组排除**。同名键 HD/SD 并存，SD 后写会覆盖 HD，症状是「所有键 0 命中」。取键必须过滤 `(hd)`。
5. **`saus/raw` 的磁盘名是 hash，不是明文**。国际服 PC 与安卓 153.6.10 都是 `<16B hash hex>.lsc`，映射在 `files_rawtype.hash`。旧文档写的「明文命名」已不成立。
