## 二、两处纠正

### 2.1 收益数值：能拿，且已经拿过

上一版引用 `_文本库说明.md` 第 22-25 行「奖励数值/掉落表不在客户端」，据此把三个场景标成 `unavailable`。**这条是错的**，属于文案层的说明，不代表数据层没有。

客户端静态表里有完整的发放链路，三者可串：

```
CampaignStageTable (4,221 关)          EventDungeonStageTable
      └ RewardId ─────────────────┐
MainQuestTable (583 条主线任务)      │
      └ RewardId ─────────────────┤
                                  ▼
                          RewardTable (28,442 包)
                                  └ Rewards[] {RewardType, RewardId, RewardValue}
                                          ├ Type 3 → 货币（99/1000/2000/3000…）
                                          └ Type 5 → ItemMaterial/Consume/Equip/Piece
                                                  └ NameLocalkey → Locale_Item.lss → 中文名
```

实测（`tmp_reward_verify.py`）：

| 指标 | 数值 |
|:--|--:|
| 奖励条目总数 | 51,654 |
| 能解析出中文名 | 43,298（**83.8%**） |
| 主奖励（信用点/战斗数据辑/芯尘/免费珠宝） | 26,699 条，覆盖全部主线关卡 |

剩余 16.2% 是活动限定货币、自选箱、特殊奖励类型，不影响主线和活动关卡的收益栏。

**已有同类产出可作先例**：`07_文本/塔奖励/`（5 塔 × 1350 层全量）、`07_文本/活动收益/`（5 个活动的关卡奖励/挑战/任务/签到/商店）。这两份报表就是靠同一套表做出来的，上一版没查。

> 唯一真的不在客户端的是**活动起止时间**（`EventManagerTable.ScheduleValue` 全服 926 条均为 `"0"`），这条上一版是对的，保留。

### 2.2 立绘：不是 4 张拼图，是 Spine

上一版说「四个 `_tex` 是一个角色的四张拼图板件」。实际打开 bundle 看：

```
spinestandingcharactergroup(hd)_assets_spine/standing/c010/00_hd_*.bundle
  → Texture2D ×1 (2048²) + TextAsset ×2 (.skel + .atlas) + Sprite ×0
```

`_tex` 是 **Spine 的图集贴图**，一张图集里放着该角色所有部件（头发/眼睛/嘴巴/武器…），由骨骼在运行时拼合。`00/01/02/03` 是**四个不同立绘**（不同破损/服装状态），不是四块拼图。

- 硬拼 atlas 的结果已验证过：`06_骨骼/待机/2B_c810_00/katana_test.png` 是散落碎片，不可用
- 走 Spine 渲染的结果：完整、干净、可出透明底

所以 `compose` 这个分类对角色立绘不成立，应改为 `render`。

## 三、立绘渲染：已验证可用

### 3.1 验证结果

用现成的 `_spine-player.js`（spine-ts 4.1）在无头 Chrome 里渲染：

| 项 | 结果 |
|:--|:--|
| 单张耗时 | **1.05 s**（20 张 21.0 s） |
| 通过率 | 20/20 |
| 输出尺寸 | 2200×3000，内容约 1717×2131 |
| 背景 | 透明（`#00000000`，角像素 RGBA=0,0,0,0） |
| WebGL | 真 GPU（ANGLE/D3D11），非软件模拟 |
| 全量预估 | 582 组 ≈ **10 分钟** |

产物质量对照：

| 来源 | 2B_c810_00 | 评价 |
|:--|:--|:--|
| `立绘HD/*_uc_tex.png` | 2048²，白底，带残留碎片（浮空辅助机、竖线） | 原料 |
| Spine 渲染 | 2200×3000，透明底，纯角色无残留 | **成品** |

### 3.2 实现要点

| 要点 | 做法 |
|:--|:--|
| 加载 | `spine.SpinePlayer` + `preserveDrawingBuffer: true`，否则 `toDataURL()` 拿到空 |
| 透明 | `backgroundColor: "#00000000"`，传 `"transparent"` 会被解析成白 |
| 一致性 | 渲染前 `animationState.current.trackTime = 0; state.update(0)`，锁到动画首帧 |
| 分辨率 | CDP `Emulation.setDeviceMetricsOverride` 设 2200×3000，窗口尺寸改不动 canvas |
| 批量 | CDP 单进程复用，`Page.navigate` 换页，比每次起 Chrome 快 10 倍 |
| 静态服务 | Node 内置 http server，`file://` 会被 CORS 拦掉二进制加载 |
| atlas 路径 | `xxx.skel` → `xxx.atlas` 同名替换即可，563/582 组是 1:1:1 |

**已落地文件**（在 `06_骨骼/`）：

- `_render.html` — 单张渲染页，参数 `?p=<路径>.skel`
- `_render_batch.js` — 批量驱动，内置静态服务 + CDP，用法 `node _render_batch.js <pageUrl> <outDir> list.txt`

## 四、取件库的数据模型

沿用「高达取件表」的四层结构：

```
板件 (bundle)  ──  零件 (object)  ──  成品 (deliverable)  ──  槽位 (slot)
  dp/xxx.bundle      skel+atlas+png      渲染出的立绘 PNG      立绘/角色/HD
```

### 4.1 可提取性分类（修正版）

| 分类 | 含义 | 典型资源 | 处理方式 |
|:--|:--|:--|:--|
| **`direct`** 直出 | 导出即成品 | 插画、图标、静态头像框、音频、文本表、**奖励数据表** | 改名归档 |
| **`render`** 需渲染 | 需播放器成像 | 角色立绘（Spine）、动态头像框序列帧 | spine-player 渲染 / 序列帧合成 |
| **`table`** 需关联 | 单表不完整，要多表 join | **关卡收益**（Stage→Reward→Item→Locale 四级）、剧情目录 | 跑关联脚本，输出扁平表 |
| **`unavailable`** 不可得 | 客户端没有 | 活动起止时间、服务器配置 | 标记，不产假数据 |

`table` 是这一版新增的类别。收益数据不是「有或没有」，而是「有四张表，需要串起来」——上一版把它误判成 `unavailable` 就是没意识到这一点。

### 4.2 版更四场景 → 槽位映射（全做）

| 版更项 | 槽位 | 分类 | 数据源 | 状态 |
|:--|:--|:--|:--|:--|

| 主线剧情文本 | `07_文本/剧情正文` | direct | `Locale_MainScenario` | 文本库有，未单独出表 |

## 五、技术选型

### 5.1 结论：pywebview + WebView2

| 方案 | 体积 | 毛玻璃 | 复用 Python | 判定 |
|:--|--:|:--|:--|:--|
| **pywebview + WebView2** | ~60 MB | CSS `backdrop-filter` 原生 | 完全复用 nk.py | **选它** |
| PySide6 | ~90 MB | 要自绘，QSS 做不出 | 复用 | 否 |
| Electron | ~150 MB | 最强 | 要重写解析层 | 否 |
| Tauri | ~10 MB | 最强 | 要重写 UnityFS/ZSTD/Spine | 否 |
| eel（参考物） | ~40 MB | 强 | 复用 | 依赖本机 Chrome，无法封装 |

跨设备 = 仅 Windows，WebView2 在 Win11 自带、Win10 需装运行时，打包时带离线安装包。

### 5.2 防卡死

**主进程永不 import UnityPy。** 实测有 39 KB 的包能让 UnityPy 直接 SIGSEGV（`0xC0000005`），Python 抓不住信号级崩溃。

```
UI 线程 ──► 任务队列 ──► 子进程池 ──► 崩了只丢当前件
   ▲                        │
   └──── 进度事件 ◄──────────┘
```

渲染走同构隔离：Chrome 进程独立，页面崩了重启页面即可。

### 5.3 打包

| 坑 | 解法 |
|:--|:--|
| onefile 解压到 C 盘 | `--runtime-tmpdir=F:/...` 或 onedir |
| WebView2 缺失 | 检测 + 离线包 |
| Chrome 依赖 | 渲染器随包带便携版 Chromium，不依赖用户浏览器 |

### 9.4 打包踩到的坑（都实测过）

| 现象 | 真因 | 解法 |
|:--|:--|:--|
| 进程活着但**没有窗口**，且无任何异常 | `--windowed` 下 `sys.stdout` 为 None，pywebview 内部一旦 print 就静默失败 | 用 `--console` 打包，启动后 `ShowWindow(hwnd, SW_HIDE)` 隐藏控制台 |
| 打包报错退出码 1 | PyInstaller `--noconfirm` 会先删同名输出目录，被本机批量删除保护拦截 | 输出目录带版本号（`dist_vN`），不复用 |
| 换电脑就打不开 | 资源库路径写死 `F:/Codex/...` | 解析顺序 环境变量 → `settings.json` → 从程序目录逐级向上找 `00_资源库`（校验含 `00_索引`+`01_角色`） |

### 9.5 渲染器踩到的坑

| 现象 | 真因 | 解法 |
|:--|:--|:--|
| 全部条目同时超时 | 传给驱动的占位 URL 写成 `http://127.0.0.1/x/_render.html`，驱动按 pathname 请求 `/x/_render.html` → 404 | 占位路径必须与真实文件一致；驱动里加 `[自检] HTTP xxx` 一行 |
| 单条坏资源拖死整轮 | 页面崩溃后 CDP 调用不返回 | 每个 CDP 调用带超时；连续 3 条失败才判定页面已废并重启 |
| 进度判据误报 | 用「新图数量」判断进展，归类坏资源那轮会被当成零进展 | 改用「待办条目数是否下降」 |

## 七、交互参考（ArcanaHelper）

`ArcanaHelper-V1.1.2.exe` 的关键设计是**先限定范围才能继续**——不让用户在 12 万文件里自由勾选，而是「选角色 → 选内容类型 → 出清单」。

取件库沿用这个约束：

```
第 1 步  选场景（主线 / 活动 / 新角色 / 头像框）
第 2 步  选范围（版本号 / 角色名 / 活动名）      ← 不选不能下一步
第 3 步  出取件表（一行一个槽位，标明原料/成品/分类/状态）
第 4 步  勾选 → 一键取件 → 进度条 + 失败清单
```
