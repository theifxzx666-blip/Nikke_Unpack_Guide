# 效率实测与瓶颈

这一篇只放实测数字，不放推测。全部在本机同一台机器、同一次会话内跑出，样本与命令附在末尾可复现。

先说结论：**单件没有提速，批量提速 12.9 倍**。原因不是工具写得快，而是把两笔「每件都要付」的固定成本从 N 次压成了 1 次。

## 一、固定成本有多贵

单件取件看起来是「定位 → 读块 → 解压 → 导出」四步，实际耗时结构完全不是这样：

| 项 | 实测 | 说明 |
| :--- | --: | :--- |
| `python -c pass` | 294 ms | 解释器启动，白付 |
| `import zstandard` | 334 ms | 增量 +40 ms |
| **`import UnityPy`** | **1,750 ms** | 增量 +1,400 ms，占单件总耗时六成以上 |
| **`load_cidx` 解析 dp 桶** | **152 ms** | 260,903 条 CIDX，每件都重读就是每件白付 |
| 一次单件取件的实际工作量 | 90~100 ms | 查键、按 `file_offset` 拼块、zstd 解压、PNG 编码 |

一次 `nk.py pull` 单件实测 1,878 / 2,311 ms，其中约 2,050 ms 是启动、导入与索引解析，真正干活不到 100 ms。

**这决定了优化方向**：任何「一件一进程」的设计都会被这两笔固定成本压死，把代码改快没意义，必须让一个进程吃多件、并且把 idx 缓存住。

## 二、实测对比

同一批 20 个立绘键（`icons-char-full(hd)_assets_c010_*`，每个 1 MB 上下，各含 1 张 1024² Texture2D）：

| 方式 | 总耗时 | 每件 | 成功 | 产出 |
| :--- | --: | --: | :-: | --: |
| 逐件独立进程（20 次 `nk.py pull`） | 52,450 ms | 2,622 ms | 19/20 | 19 PNG |
| `batch` 串行 | 4,059 ms | 203 ms | 20/20 | 20 PNG |
| `batch --jobs 4` | **3,198 ms** | **160 ms** | **20/20** | **20 PNG** |

复测 4,005 / 4,059 / 4,459 ms，稳定。

**20 件：串行 12.9 倍，四进程 16.4 倍。**

件数上去以后差距拉得更开。100 个立绘键：

| 方式 | 总耗时 | 每件 | 产出 |
| :--- | --: | --: | --: |
| 逐件独立进程（按 2,622 ms/件 推算） | ≈ 262,200 ms | 2,622 ms | — |
| `batch` 串行 | 15,560 ms | 155 ms | 100 PNG |
| `batch --jobs 4` | **5,032 ms** | **50 ms** | **100 PNG** |
| `batch --jobs 8` | 4,654 ms | 46 ms | 100 PNG |

**100 件四进程约 52 倍，八进程约 56 倍**——八进程相对四进程只再快 8%，边际已经很薄，默认取 4。

两段提速各自来源清楚：

| 阶段 | 省下（20 件口径） | 来源 |
| :--- | --: | :--- |
| 20 次进程 → 1 次进程 | 45.1 s | 20 × (294 + 1,750) ms 的解释器与 UnityPy 导入 |
| idx 每件重读 → 只读一次 | 3.3 s | 20 × 152 ms 的 CIDX 解析（260,903 条） |
| 串行 → 四进程 | 0.9 s | 按件并行，PNG 编码是 CPU 密集，这部分能真并行 |

单件链路另有对照（同一键，两种实现）：

| 实现 | 耗时 | 备注 |
| :--- | --: | :--- |
| 旧 `tmp_fetch_bundle.py --save` | 2,130 / 2,056 ms | 一条命令完成取件+导 PNG |
| 新 `nk.py get` + `nk.py export` | 428 + 1,449~1,871 ms | 两条命令，固定成本付两遍 |
| 新 `nk.py pull` | 1,878 / 2,311 ms | 合一后回到一条命令 |

单件上三者基本持平——固定成本都在，怎么组合都跳不过去。**这本身就是结论：单件优化没有意义，只有批量有意义。**

### 批量为什么不是无限快

固定成本付一次后，串行总耗时 ≈ `2,050 + N × 150 ms`；四进程再把它压到 `≈ 2,050 + N × 50 ms`。

| 件数 | 逐件独立进程 | batch 串行 | batch 4 进程 | 最大倍数 |
| --: | --: | --: | --: | --: |
| 1 | 2.6 s | 2.1 s | 2.1 s（退回串行） | 1.2x |
| 20 | 52.4 s（实测） | 4.1 s（实测） | 3.2 s（实测） | 16.4x |
| 100 | 4.4 min（推算） | 15.6 s（实测） | 5.0 s（实测） | **52x** |
| 1,000 | 44 min（推算） | 2.6 min | ≈ 52 s | ≈ 50x |

**上限由两件事决定**：单件的真实工作量（约 150 ms，串行时省不掉）和并行能压到多低。
四进程实测 50 ms/件，已接近磁盘与 CPU 的实际上限——八进程只再快 8%。

件数少于 `2 × jobs` 时自动退回串行：四进程 spawn 的开销约 1 s，件数太少会净亏。

## 三、正确性上的差别（不是速度）

旧脚本 `tmp_fetch_bundle.py` 对失效键**静默返回 0，退出码 0**。本次实测踩到两次：

1. 用完整键 `icons-char-full(hd)_assets_c010_00_435214c0…bundle` 调用 → 零输出、零报错。原因是客户端更新后 bundle 哈希从 `435214c0…` 变成 `f17169d8…`，键已失效。
2. 键表用 Windows 默认 CRLF 写出，shell 逐行读取时尾部带 `\r` → 20 件全部静默失败，耗时 5.4 秒、看起来「跑完了」。

这两次的共同点是**失败长得像成功**。新工具的处理：

- `find` 用前缀检索，哈希变了照样命中；
- `pull` 在清单里查不到键直接抛 `KeyError`，不返回空；
- `batch` 内部对每行 `strip()`，CRLF 免疫；失败逐条记账并在结尾回报 `fail` 数与原因。

## 四、国服索引：从无到有，收益最大但代价前置

国服缓存目录名是随机哈希，与 bundle 名无确定关系（md5 / sha1 各变体实测均不命中），只能读包内对象名反查，也就是必须建索引。

### 建索引是一次性投入，回本极快

| 方式 | 单件定位耗时 | 说明 |
| :--- | --: | :--- |
| 暴力扫（无索引） | 约 3.5 分钟（期望） | 实测 52 包/秒、扫 1,201 包仍未命中；命中位置均匀分布，期望扫一半即 11,105 包 |
| 索引命中 | **约 300 ms** | 其中 294 ms 是解释器启动，sqlite 查询本身 < 10 ms |

**约 700 倍**。只要拆包任务超过两次，建索引就回本。

### 并发度实测

400 包 / 188 MB 样本，单进程与多进程吞吐：

| 进程数 | 吞吐 | 加速 |
| --: | --: | --: |
| 1 | 39 包/秒 | 1.00x |
| 2 | 66 包/秒 | 1.70x |
| 4 | 94 包/秒 | 2.42x |
| **8** | **101 包/秒** | **2.61x** |
| 10 | 94 包/秒 | 2.44x |

**加速在 4 进程后饱和**，8/10 进程只是徒增内存与磁盘争抢。默认并发已改为 4。

### 两个被证伪的优化方向

| 设想 | 实测 | 结论 |
| :--- | :--- | :--- |
| 只读 `AssetBundle` 对象、不遍历资源，应该快很多 | 44 包/秒，**比原版 52 包/秒更慢** | 瓶颈在 `UnityPy.load` 读整文件，不在反序列化。省对象没用 |
| 某个超大包拖死了索引 | 31 个 16~128 MB 的大包全部 < 1.8 s，最大 109 MB 只用 1.78 s | 没有卡死包。之前的「40 分钟不收敛」是调度与不可观测，不是数据 |

### 慢的真正原因：一个 39 KB 的包能让 UnityPy 段错误

这是整件事最反直觉的一环，也是「跑 40 分钟不收敛」的唯一真因。

定位过程：

| 步骤 | 现象 |
| :--- | :--- |
| 1. 怀疑大包拖尾 | 31 个 16~128 MB 的包全部 < 1.8 s，最大 109 MB 只用 1.78 s → **证伪** |
| 2. 怀疑解析方式低效 | 只读 `AssetBundle` 对象 44 包/秒，比原版 52 包/秒更慢 → **证伪** |
| 3. 检查卡在哪 | 索引稳定停在 22,172/22,210，剩下 38 个包合计仅 **14.1 MB**，最大 4.49 MB |
| 4. 逐包单独跑 | 38 个包**全部 1.8 秒内成功** |
| 5. 同进程连续跑 | 跑到第 15 个包时 **Segmentation fault（exit 139）** |

那第 15 个包就是元凶：

```
39,471 字节
cache\1de07cfc1025b6941228273faef9a4ca\49a8af4ff776d0deb02706f5ddad1cd3\__data
头部 UnityFS / 版本 8 / 5.x.x / 2021.3   ← 完全正常的格式
```

**它单独跑必崩，格式化完全合法，体积只有 39 KB。** Python 抓不住 SIGSEGV，于是：

- 用 `Pool` 时：一个 worker 死掉，主进程卡在 `imap_unordered` 等结果，**永远不返回**；
- 用单进程时：整个索引进程直接消失，前面几万包的成果全部作废；
- 重跑：它还在那儿，于是每次都「跑到差不多的位置就不动了」。

### 解法：进程隔离 + 崩溃记账

把分片交给独立子进程，而不是线程池里的 worker：

```
主进程 → 4 个子进程（各吃一份路径，各写独立 sqlite）
       → 子进程退出码非 0（3221225477 = 0xC0000005 访问违例）
       → 主进程对该分片逐包开子进程重试
       → 仍然崩的那个包：确认是毒包，写进 done 表标记跳过，继续
```

实测收尾表现：

```
待处理 1 包，切 1 片
分片 0 退出码 3221225477（疑似毒包段错误），转逐包隔离
毒包（段错误，已标记跳过）: ...\49a8af4ff776d0deb02706f5ddad1cd3\__data
{"bundles": 22210, "names": 132516, "skipped": 1, "poison_parts": 1, "seconds": 3.8}
```

**3.8 秒收尾，不再卡死。**

### 最终索引（国服 WeGame 版，全量完成）

| 项 | 值 |
| :--- | :--- |
| 已索引包 | **22,210 / 22,210** |
| 不同对象名 | **132,516** |
| 毒包（跳过） | 1 |
| 库文件 | 335 MB（sqlite + WAL） |
| 建库总耗时 | 约 28 分钟（其中 27 分钟耗在毒包导致的卡死上；去掉这一项后实际工作量约 4 分钟） |

> 换句话说：**这个 bug 让索引慢了 7 倍，而且表现成「没报错、只是很慢」，最难排查。**

### 第二个坑：路径写法一换，续跑就静默全废

续跑去重原本按路径字符串比对。但同一个文件有多种写法：

```
E:/WeGameApps/rail_apps/.../cache\0031b9cd...\...\__data   ← 根用正斜杠 + join 补反斜杠
E:\WeGameApps\rail_apps\...\cache\0031b9cd...\...\__data   ← 全反斜杠
```

结果：某次用 `E:/...` 建的索引，下次用 `E:\...` 续跑时 **22,210 个包全部被判为「未处理」**，
从零重跑——而且没有任何报错，只是又慢了一次。

修复：`path_key()` 统一做 `abspath → normpath → normcase`。
`done` 表存规范化键，`files` 表仍存原路径（保证美观且能直接打开）。

**这两个 bug 有同一个特征：不报错，只是慢。** 排查成本远高于修复成本。

### 吞吐会随时间衰减

同一次全量建库，吞吐从 84 包/秒一路降到 24 包/秒：

| 进度 | 吞吐 |
| :--- | --: |
| 5,000 包 | 84 包/秒 |
| 10,000 包 | 40 包/秒 |
| 15,000 包 | 30 包/秒 |
| 22,000 包 | 24 包/秒 |

原因没有完全查清，候选是 sqlite 大表插入变慢与磁盘缓存耗尽叠加。
这解释了为什么「按前期速度估算 ETA」会严重低估总时长——ETA 必须按滚动窗口算，不能按全程均值。

## 五、还剩多少优化空间

按收益排序，都是可做的：

| # | 优化 | 预期收益 | 成本 |
| :-: | :--- | :--- | :--- |
| 1 | 导出只落需要的类型（当前无差别扫全部对象） | 大包场景省 30~50% 时间 | 中，加类型过滤参数 |
| 2 | 国服索引按需增量：只索引「清单里有、缓存里没命中」的包 | 索引时间与缺口成正比，不再是全量 | 中 |
| 3 | 索引插入改批量事务（当前逐包 commit） | 可能缓解吞吐衰减，省 20~40% 建库时间 | 低 |
| 4 | 预编译 UnityPy 导入（`-X importtime` 分析后裁依赖） | 省几百 ms，影响单件与每轮批量的启动段 | 低但要验证 |
| 5 | 毒包黑名单跨库共享 | 换机器/换版本时不必重新踩一次 | 低 |

已完成的（写在这里防重复劳动）：

| 项 | 效果 |
| :--- | :--- |
| `get` + `export` 合并为 `pull` | 单件少一次进程，2.6 s → 1.9 s |
| `store.cdb.idx` 模块级缓存（按 路径+mtime 失效） | 每件省 152 ms，20 件省 3.3 s |
| `batch` 按件多进程 | 100 件 15.6 s → 5.0 s |
| 索引落 sqlite + 分片续跑 | 中断不再全废，查询 < 10 ms |
| 分片 subprocess 隔离 + 毒包记账 | 单个毒包不再拖死整轮，3.8 s 收尾 |
| `path_key()` 规范化续跑键 | 路径写法变化不再导致静默全量重跑 |

**不建议做的**：

- 把 `UnityPy.load` 换成手写 UnityFS 解析器——大包实测 1.78 s，收益远小于维护成本；
- 加并发到 8 以上——实测已回落（101 → 94 包/秒）；
- 给单件做缓存预热——真正的一次性任务占比太低，且单件成本已由 `pull` 兜住；
- 试图用 `try/except` 捕获那个毒包的崩溃——SIGSEGV 不是 Python 异常，只能进程隔离。

## 六、复现

```bash
PY=F:/Codex/Supports/venv_assetparse/Scripts/python.exe
R="D:/PanDownload/Nikke_local/NIKKEG"

# 单件：一条命令取件+导出（1.9 s，其中 1.75 s 是 import）
$PY tools/nk.py pull --scene intl-pc --root "$R" --bucket dp "<完整键>" -o out/one

# 批量：一个进程吃整份键表（20 件 3.2 s，对比逐件 52.4 s；100 件 5.0 s）
$PY tools/nk.py batch --scene intl-pc --root "$R" --bucket dp keys.txt -o out/all --jobs 4

# 国服：建索引（分片 subprocess 隔离，崩了只丢一个包，可中断续跑）
$PY tools/nk.py cnindex --root "E:/WeGameApps/rail_apps/胜利女神：新的希望(2002017)/nikke_Data/runtime_data/cache" \
    -o build/cn_index.sqlite --jobs 4

# 国服：按对象名取件（索引建好后 < 100 ms）
$PY tools/nk.py cnget --root "<cache 根>" "<32hex>.bundle" -o out/x.bundle
```

固定成本基线可自行复测：

```bash
for t in "pass" "import zstandard" "import UnityPy"; do
  S=$(date +%s%N); $PY -c "$t"; E=$(date +%s%N); echo "$(( (E-S)/1000000 )) ms  $t"
done
```
