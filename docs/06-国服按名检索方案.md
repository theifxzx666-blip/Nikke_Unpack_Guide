# 国服按名检索方案

> 状态：方案，未实施。摸底数据采集于 2026-11-05，国服 WeGame 版（`胜利女神：新的希望(2002017)`）。
> 文中每个数字都是当场量出来的，不是推算。

---

## 一、要做什么

给国服补一个「按名字找资源」的能力，形状和国际服那条 `find → keys → batch` 一样：

```bash
# 国际服现在就能这样
python tools/nk.py find "marian" --all --keys keys.txt
python tools/nk.py batch keys_core.txt --bucket core -o out/ --skip-missing

# 国服缺的就是第一句
python tools/nk.py find "marian" --scene cn-pc --keys cn_keys.txt
```

具体交付三样：

1. 一个**语义名清单**：从国服的 `catalog.json` 里把 22,015 个资源包的可读名字抽出来，落进 `cn_index.sqlite`。
2. 一个 **`find` 的国服分支**：按名字搜，直接给出「这个资源在哪、多大、能不能取」。
3. 一条**取件链路**：命中后接现有的 `cnget`，不用再手抄 32 位哈希。

---

## 二、为什么做

### 现在国服的状况

国服解包目前只有一条路：**先知道 32 位哈希，才能取件**。

```
cnget <32hex 或对象名> -o x.bundle
```

而玩家脑子里的问题是「MARIA-n 这个活动的 UI 在哪个包里」。这两件事之间没有桥——哈希是内容的指纹，猜不出来，也算不出来（已经试过对清单算 md5 / sha1，全部不命中）。

于是每次采资源都变成：翻日志、翻旧记录、或者干脆整包扫一遍。

### 国际服已经解决了，国服没有

国际服的 `catalog.ndb` 解密后是一张 SQLite，`files_chunktype.key` 就是完整可读的键名：

```
eventui-marian_assets_story_event_list_marian_part2_9fac3295….bundle
```

一行 `LIKE '%marian%'` 就出结果。国服没有这张表。

### 更要紧的是：国服的清单其实有名字，只是没人去读

摸底发现 `nikke_Data/StreamingAssets/aa/catalog.json`（41.3 MB）里存着 49,497 条资源路径，其中 **22,015 条**是这种形状：

```
{NK.Addressable.HostConst.HostCoreLoadURL}\eventui-marian_assets_story_event_list_marian_part2_9fac3295….bundle
```

名字是完整的、可读的、带活动前缀的。**它一直是明文**，只是没人把它接到缓存上。

所以这件事的成本不是「难」，是「没人做」。

---

## 三、做完有什么好处

| 现在 | 做完 |
| :--- | :--- |
| 只能按 32 位哈希取件 | 按 `marian` / `eventui` / `story_event` 这类词搜 |
| 想找某个活动的资源，靠翻记录或整包扫 | 一条命令，百毫秒级出清单 |
| 不知道「这个资源本地有没有」 | 直接标注「可拉 / 未下载」，不用试错 |
| 每次捡到哈希要手抄进命令 | 生成键表，直接喂给 `cnget`，可批量 |

一句话：**把国服的「知道哈希才能取」变成「知道名字就能搜」，并且和国际服共用同一套命令形状。**

顺手还能修掉一个隐性浪费：搜到 20 个资源却不知道其中 8 个本地没有，只能一个个试。

## 四、怎么做

### 4.1 先看清数据长什么样

国服客户端里跟「资源清单」有关的东西一共三处，作用完全不同，容易混：

| 位置 | 是什么 | 有没有用 |
| :--- | :--- | :--- |
| `StreamingAssets/aa/catalog.json` | Unity Addressables 的主清单，41.3 MB 明文 JSON | **主力**，22,015 个包的语义名在这 |
| `runtime_data/saus/*/asset-catalog-*.cat` | 增量补丁清单，SQLite 格式，标签是 `required` / `add` / `c010` | 只描述「这次更新补了哪些」，不是主目录，先不碰 |
| `runtime_data/cache/<32hex>/<32hex>/__data` | 真正下载到本地的包体，22,210 个 | 取件目标 |

`catalog.json` 里有 13 个顶层字段，只有 `m_InternalIds` 可以直接用——它是一个 4.2 MB 的字符串数组，每条就是一个资源的路径。另外三个 `m_KeyDataString` / `m_BucketDataString` / `m_EntryDataString` 是 base64 编码的二进制索引，**这个方案不需要解析它们**，因为我们要的名字已经在 `m_InternalIds` 里了。

### 4.2 关键发现：两套哈希对不上，但名字对得上

这是整个方案的地基，必须说清楚。

清单里每条 bundle 的名字末尾带 32 位哈希：

```
eventui-marian_assets_..._part2_9fac3295c22c0a27ebc292cd99c0…bundle
```

按直觉，拿这个哈希去 `cache/` 找同名目录，应该能对上。**实测对不上，一个都不中。**

缓存目录名是另一套哈希。随机抽 5 个缓存目录名去 `catalog.json` 全文搜索，出现次数都是 0。

但换个比法就通了——**比名字中间的语义部分**：

| 清单里的完整名 | 去掉前缀和哈希 | 索引里能找到吗 |
| :--- | :--- | :-: |
| `audiogroupscenario_assets_sfx_scn_mariancannon_67cecf74….bundle` | `sfx_scn_mariancannon` | 找到 |
| `audiogroupui_assets_event_lastkingdom_minigame_h_marian_t_burst_1_5a7190f3….bundle` | `event_lastkingdom_minigame_h_marian_t_burst_1` | 找到 |

国服清单里 9 个带 `marian` 的包，9 个都能在索引里找到对应的包内对象名。**一一对应，没有例外。**

这就是桥：**哈希是两套，语义名是同一套。**

### 4.3 抽样验证：桥接率 66%

拿 400 个随机 bundle 做过验证：

| 匹配方式 | 命中 | 占比 |
| :--- | --: | --: |
| 对象名精确相等 | 208 | 52.0% |
| 放宽到包含匹配，再补 56 个 | 264 | **66.0%** |
| 仍然对不上 | 136 | 34.0% |

**三分之一的资源「能在清单里看到名字，但落不到本地包」。**

这个数字决定了方案的边界，所以必须先讲清楚原因。目前判断有三种可能，还没有逐一拆开验证：

1. **包本来就没下载**——`catalog.json` 记录的是「这个版本下发过什么」，而 `cache/` 里只有玩家实际用过的。清单 22,015 个包对缓存 22,210 个包，总量接近，但未必是同一批。
2. **包内对象名不一定是语义名**——有些包（尤其是纯贴图包）内部只有一个 `<32hex>.bundle` 和若干空名对象，没有可读名字。
3. **拆名规则不够细**——现在按「最后一个 `_assets_` 之后全部保留」拆，有些资源的实际对象名更短，比如带了子目录前缀。

第 1 种不是缺陷，第 2、3 种才是要补的。

### 4.4 三步落地

**第一步：建语义表（改 `cnindex`，约 40 行）**

在主索引旁加一张表，把清单拆开存进去：

```sql
CREATE TABLE cn_catalog (
    bundle TEXT PRIMARY KEY,   -- 完整 bundle 名，含哈希
    group  TEXT,               -- 前缀，如 eventui-marian
    objname TEXT,              -- 拆出来的语义名
    hash   TEXT                -- 末尾 32 位
);
```

解析 `catalog.json` 只要 **0.08 秒**，抽取 22,015 条，落表后约 4 MB。这是纯增量，不动现有 `files` 表。

**第二步：`find` 加国服分支（约 50 行）**

搜的时候三路并查，按可信度排序输出：

| 路径 | 查什么 | 输出什么 |
| :--- | :--- | :--- |
| A | `cn_catalog.bundle LIKE '%词%'` | 资源存在，给出完整名；再按 objname 找 `files` 定位 |
| B | `files.name LIKE '%词%'` | 直接命中包内对象名，给出 `__data` 路径 |
| C | A 命中但 B 没命中 | 标「清单有、本地无」，列出包名让用户决定要不要等游戏内下载 |

输出格式跟国际服完全一致（一行一个键，`--keys` 落文件），上层脚本不用改。

**第三步：接 `cnget`**

命中的键直接喂 `cnget`，`--keys` 模式一次取一批。这一步 `cnget` 已经支持单件，补一个批量循环即可（约 20 行，复用国际服 `batch` 的骨架）。

### 4.5 工作量与验收

| 项 | 估量 | 验收标准 |
| :--- | :--- | :--- |
| 语义表 | 40 行 | 表内 22,015 行，与 `m_InternalIds` 计数一致 |
| `find` 国服分支 | 50 行 | 搜 `marian` 返回 9 条，且每条都能落到真实 `__data` |
| 批量取件 | 20 行 | 键表 9 条，9/9 取到，`head` 为 `UnityFS` |
| 文档 | — | `SKILL.md` 快速开始加一段，`04-tooling.md` 状态行跟进 |

一天之内可以做完并验证。

## 五、后续怎么复用

这一节是重点，因为做完之后真正省时间的是「以后每次都不用重来」。

### 5.1 一次建表，长期有效

`cn_catalog` 表跟着 `cn_index.sqlite` 走。索引本身就是一次性的（22,210 个包扫一遍），语义表加进去只要多几秒。

**版本更新后**：`catalog.json` 会变（哈希变、新资源加入），重跑一次 `cnindex` 就同时更新两张表，不用额外步骤。这一点跟现有的「续跑」机制兼容——`done` 表记的是已经扫过的包，`cn_catalog` 是全量重建，互不干扰。

### 5.2 四场景共用同一套输出

做完之后，四个场景的命令形状完全一致：

```bash
nk find "<关键词>" --scene intl-pc   --keys k.txt   # 国际服 PC
nk find "<关键词>" --scene intl-adb  --keys k.txt   # 国际服安卓
nk find "<关键词>" --scene cn-pc     --keys k.txt   # 国服 PC
nk find "<关键词>" --scene cn-adb    --keys k.txt   # 国服安卓
```

上层脚本（采集、归档、入库登记）只认键表格式，**不用区分是哪个服**。这是这次重构「2×2 矩阵」的初衷，国服这条补上之后才算真正闭合。

安卓国服走 ADB 时，只需要把 `catalog.json` 从设备拉到本地一次（约 41 MB），后续查表都在本地，不用连着手机。

### 5.3 这套「哈希不同、名字相同」的判断可以复用

这次踩到的坑——**两个系统的哈希对不上，但语义名是同一套**——不只国服有。以后再遇到「清单和缓存对不上」的情况，先用语义名交叉验证一遍，比对着哈希猜快得多。

写进文档，是为了下次不用重新发现。

### 5.4 不做什么

保持克制，几条明确不碰的：

- **不解析 `m_KeyDataString` / `m_BucketDataString` / `m_EntryDataString`**。那是 Unity 内部 key→entry 映射，我们要的路径已经在明文里，解析它只增加出错面。
- **不碰 `saus/*.cat`**。它是增量补丁清单，标签是 `required` / `add`，描述的是「这次更新补了哪些包」，不构成完整目录。把它混进来只会让结果不确定。
- **不为 34% 对不上的资源做猜测性匹配**。宁可明确报「清单有、本地无」，也不放松到模糊命中——错配一个包比漏一个更费时间。

## 六、一个必须先确认的前提

摸底时发现一件比方案本身更该先说的事：

**国服当前版本里没有 MARIA-n 活动。**

- `catalog.json` 全文搜 `marian`，只有 **9 条**，全是 4 周年小游戏的音频（`sfx_scn_mariancannon`、`event_lastkingdom_minigame_h_marian_t_burst_1` 这类）。
- 索引里搜 `marian`，同样是这 9 个对象名，一一对应。
- 没有活动 UI、没有剧情 CG、没有剧情场景 Spine。

也就是说，同样的关键词，国际服有 198 个包，国服只有 9 个——**不是工具的问题，是国服没上这个活动**。

所以这个方案对**已经结束的活动**没有帮助，它的价值在于：

1. 国服以后上线的活动，资源一到本地就能立刻按名定位，不用再翻哈希；
2. 国服已有的资源（比如 4 周年、常驻角色）现在就能按名搜，这是实打实立刻可用的；
3. 四场景命令形状统一，采集脚本不用分叉。

如果只是为了找 MARIA-n，那国服这边确实没有可找的东西——这批资源只在国际服。

## 六、一个前置问题，已经先解决了

写这份方案的过程中冒出来一件比方案本身更基础的事：**开工前没人确认资源在哪个服**。

同样的关键词，国际服 198 个包，国服 9 条音频。如果一上来就认准国服，翻到最后也是空的。
这不是判断失误，是流程里缺了一步。

现在 `nk.py` 有 `locate`：

```bash
python tools/nk.py locate marian --intl-root "<国际服根>" --cn-root "<国服根>"
```

0.4 秒输出两服的命中数、类型构成（国际服 `scenariobackground:98 eventui-marian:42 …`，
国服 `event:5 sfx:4`）和一句结论。上面整段摸底，现在是一条命令。

只给一侧路径时，另一侧明确报「未检查」，不会静默返回 0 条误导人。

完整采集流程见 [07-采集工作流.md](07-采集工作流.md)。本文剩下的部分——建语义表、
接 `find`、国服批量取件——仍未实施。
