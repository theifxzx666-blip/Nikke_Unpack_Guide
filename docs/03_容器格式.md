## 一、设备侧路径

客户端包名以实际安装为准（示例为国际服）。根路径记作 `$P`：

```
$P = /storage/emulated/0/Android/data/<包名>
```

```
$P/
├── cache/
│   └── StaticData.pack              ← 静态数值表（加密 zip）
├── files/
│   ├── com.shiftup.addressables/
│   │   ├── catalog.db               ← Addressables 主清单（SQLite，8,788,006 B）
│   │   └── catalog.db.nds           ← 96 B，签名块，不参与解密
│   └── com.shiftup.patch/
│       ├── core/
│       │   ├── catalog.ndb          ← 桶清单（NKDB）
│       │   └── chunk/
│       │       ├── store.cdb        ← 数据体（多个 pak 拼成）
│       │       └── store.cdb.idx    ← 块索引（CIDX）
│       ├── dp/    ├── fd/    ├── en/    ├── ja/    ├── ko/
│       └── saus/
│           ├── catalog.ndb
│           └── raw/                 ← 明文命名！Locale_*.lsc / perm_*.lsc / event_YYMMDD.lsc
```

### 三个容易找错的地方

1. **`StaticData.pack` 在 `cache/` 下，不在 `files/` 下。**
2. **`saus` 的文本走 `raw/` 明文目录**，不经过 `store.cdb`，
   也不在 `files_chunktype` 里（该桶 `files_rawtype` 有 192 条，`files_chunktype` 只有 1 条）。
3. `catalog.db`（addressables）和 `<桶>/catalog.ndb` 是**两套完全不同的清单**，
   格式也不同（前者是 SQLite 明文，后者是 NKDB 加密）。别混。

### 拉取权限

外部存储的 `Android/data` 目录虽然属主是 app，直接 `adb pull` 会 Permission denied。
国产 ROM 对该目录的封锁更严，连 `adb shell` 也可能读不到。

稳妥做法：

```bash
adb shell su -c "cp <源> /sdcard/_tmp && chmod 666 /sdcard/_tmp"
adb pull /sdcard/_tmp <本地>
```

`chmod 666` 必须做 —— `su -c` 出来的文件属主是 root，不改权限 pull 会失败。

> 不需要解密，只需要「搬出来」的场合，Android 10 及以下机型通常可以直接 pull。
> 全量几十 GB 的素材，root 基本是最省事的一条路。

## 二、四级清单串联

要拿到一个具体资源，必须串四层。少一层就定位不到。

```
① Addressables 主清单   catalog.db（SQLite）
   asset address ──> internal_id（bundle 内部名）
        │
        ▼
② 桶清单                <桶>/catalog.ndb（NKDB → SQLite）
   key ──> file_id ──> chunk_file_map ──> [chunk_id, file_offset]
        │                                    │
        │                                    ▼
        │                             chunks: hash / original_size / compressed_size
        ▼
③ 块索引                <桶>/chunk/store.cdb.idx（CIDX，二进制）
   hash ──> (pos, compressed_size)
        │
        ▼
④ 数据体                <桶>/chunk/store.cdb
   pos ──> dd 切块 ──> zstd 解压 ──> 按 file_offset 顺序拼接 ──> .bundle
```

### ② 的 SQLite 表结构（`<桶>/catalog.ndb` 解密后）

以主桶为例：

| 表 | 行数 | 字段 |
| :--- | --: | :--- |
| `files_chunktype` | 27,905 | `file_id, key, group_id` |
| `files_rawtype` | 2 | `file_id, key, hash, extension, size, group_id` |
| `chunks` | 192,232 | `chunk_id, hash, original_size, compressed_size, pak_id, pak_offset` |
| `chunk_file_map` | 298,179 | `chunk_id, file_id, file_offset` |
| `paks` | 6 | `pak_id, pak_name`（32 位 hex 命名） |
| `groups_chunktype` | 5 | `group_id, group_name` |

`key` 的形态是 `<分组>_assets_<分组>/<bundle 文件名>`：

```
spotmonster(hd)_assets_spotmonster/bbg003_2ef1....bundle
```

**`chunk_file_map.file_offset` 是该 chunk 在「目标文件内」的写入偏移** ——
拼装时必须按它排序并校验连续性，否则会静默产出内容错乱但体积正常的 bundle。

### ① 的 SQLite 表结构

标准 Unity Addressables `ContentCatalogData`：

`keys`(101,985) / `key_entries`(253,760) / `entries`(62,728) /
`internal_ids`(60,099) / `types`(130) / `provider_ids` / `resource_prov` / `entry_data`

用途是「人类可读的资源地址 → bundle 内部名」。

**实战上可以跳过 ①** —— 取件脚本直接用 `files_chunktype.key` 做通配匹配，
因为这些 key 本身就带完整路径，够用。只有需要按 Addressables 地址精确反查时才用得上。

## 三、三种容器的二进制格式

### 3.1 NKDB（`catalog.ndb` / `*.lsc` / `catalog.db`）

| 偏移 | 长度 | 含义 |
| --: | --: | :--- |
| 0 | 4 | 魔数 `NKDB` |
| 4 | 4 | version（**大端**，实测 1） |
| **8** | **16** | **AES-128 密钥（明文就写在这）** |
| 24 | 4 | segment_size（大端，实测 65,536） |
| 28 | 4 | segment_count（大端，实测 316） |
| 32 | N×L | 段偏移表，大端 |

`L` 不是固定值，按总长动态决定：

```python
length_byte_count = 5 if segment_size * segment_count > 0xFFFFFFFF else 4
```

偏移表是**累积式**的：读到第 i 个值就是第 i+1 段的结束位置，段长 = 差值。

每段解密：

```python
iv  = struct.pack('<ii', segment_index, segment_offset) + b'\x00' * 8
seg = AES.new(aes_key, AES.MODE_OFB, iv).decrypt(seg)
try:    seg = zlib.decompress(seg)      # 压过就解，没压就原样
except Exception: pass
```

#### 关键结论：NKDB 没有全局密钥

密钥是生成该文件时随机生成、**明文写在偏移 8**，每个文件都不一样。

实测三个文件三把不同的钥匙（这里只给形态示意，你自己读文件头就能拿到）：

| 文件 | 密钥 |
| :--- | :--- |
| `addressables/catalog.db` | 16 字节，从偏移 8 读出 |
| `Locale_Monster`（某个 `.lsc`） | **与上面不同** |
| `Locale_Stage`（另一个 `.lsc`） | **与前两个都不同** |

所以「找一把万能密钥」这条路不存在。**正确做法是解每个文件时都读它自己的头。**

验证：`catalog.db` 实测 8,788,006 B → 解出 20,709,376 B 明文 SQLite，
而 `316 × 65,536 = 20,709,376`，**误差为零**。

### 3.2 CIDX（`store.cdb.idx`）

```
0   4B  魔数 "CIDX"
4   4B  未用（实测 01 00 00 00）
8   4B  entry_count，**小端**
12  N×28B  条目，**全部小端**
```

每条 28 字节：

```
+0   16B  chunk hash
+16   8B  pos            ← 在 store.cdb 里的绝对字节偏移
+24   4B  compressed_size
```

实测主桶 idx = 4,993,324 B，声明 178,332 条，`12 + 28 × 178,332 = 4,993,308`，
**尾部多 16 字节**（疑似 CRC，读取时忽略即可）。

> ⚠ **端序：CIDX 是小端，NKDB 是大端。**
> 搞混会直接算出天文数字的偏移，然后 dd 出一个空文件，且不报错。

### 3.3 `store.cdb` 与多个 pak 的关系

`store.cdb` 是把多个 `pak` **按 id 顺序紧密重排后拼成的单文件**。

实测三点吻合（主桶 6 个 pak）：

| pak | 块数 | Σcompressed_size | store.cdb 内起点 |
| --: | --: | --: | --: |
| 1 | 36,358 | 1,073,728,559 | 0（首块 pos = 256） |
| 2 | 34,115 | 1,073,729,306 | 1,073,728,815 |
| 3 | 42,637 | 1,073,739,813 | 2,147,458,121 |

推得：

```
pak_n 起点 = 256 + Σ_{i<n} Σ(compressed_size of pak_i)
```

`256` 字节是全局头，之后每个 pak 数据紧密相接，**pak 之间没有 padding**。

#### ⚠ `pak_offset` ≠ 上面这个紧密偏移

`chunks.pak_offset` 是**原 pak 文件内**的偏移，pak 内部存在空隙
（`max(pak_offset + comp)` 比 `Σcomp` 大 25 万字节量级）。

所以**不能用 `pak_offset` 直接去 `store.cdb` 里捞，必须走 idx**。

### 3.4 数据块

每块是 **zstd 单帧**，解压目标长度 = `chunks.original_size`。

实测主桶单块：min 2 B / **max 1,048,576 B（正好 1 MiB）** / 平均 83,684 B ——
块上限就是 1 MiB。

## 四、取件算法与三道硬约束

```
fetch(bucket, key):
  1. catalog 查 file_id → chunk_file_map 按 file_offset 排序 → [(hash, orig, comp)]
  2. idx 查每个 hash → pos
  3. 按 pos 排序，间隔 > 32 MiB 就断成新的一批（减少 dd 次数）
  4. 每批：起点向下对齐 4096，dd bs=4096 skip=起点/4096 count=块数
  5. pull 回来 → 按 (pos - 对齐起点) 切片
  6. zstd 解压，断言 len == original_size
  7. 断言 file_offset == 已写入长度（顺序连续），拼接
```

### 三道约束，违反任一条都会静默出错

**① `dd` 必须 4096 对齐**

`skip` 单位是 4096 字节块，不是字节。

```python
clo_al = (clo // 4096) * 4096
skip   = clo_al // 4096
```

**② 拼装必须验 `file_offset` 连续**

只解压不验序，遇到 chunk 顺序错乱会产出一个**长度正确、内容错位**的 bundle。
UnityPy 可能仍然打得开，错误延后到解析阶段才爆 —— 那时候你已经导了几百张图了。

**③ `chmod 666` 必须先做**

`su -c 'dd ... of=/sdcard/x'` 出来的文件属主是 root，不改权限 pull 必失败。

### 批量优化

按 `pos` 排序后，间隔 > 32 MiB 断批。同一批用一次 `dd` 覆盖多个块，
能把「每块一次 adb 往返」压到「每批一次」。取 50 个 BOSS 模型时差距是几十倍。

## 六、两条例外链路

### 6.1 `saus/raw` —— 文本表不走 chunk

`saus` 的 `files_rawtype` 有 **192** 条，全部**明文命名**，直接躺在 `$P/files/com.shiftup.patch/saus/raw/` 下：

```
Locale_*.lsc           界面 / 表名本地化
perm_*.lsc             权限 / 常驻文本
event_YYMMDD.lsc       每期上架的 BANNER 清单
lss/*SearchTable_<语>.lsc   搜索表
```

**这批文件直接 pull，不用 dd、不用 zstd、不进 idx。** 拿到手只有一层 NKDB 要解。

实战价值很大：相邻两期 `event_*.lsc` 的 `sprite.name` 做集合差 = 本期新上的卡池 / 皮肤。
**分钟级操作，不需要全量基线。**

### 6.2 `StaticData.pack` —— 唯一的双层 AES

位置：`$P/cache/StaticData.pack`。

```
第 1 层（剥壳）：
  k = PBKDF2(PRESHARED_64B, SALT2_32B, dkLen=32, count=10000, SHA256)
  d = AES-256-CBC(k[:16], iv=k[16:32]).decrypt(raw)   → 去 PKCS7
  d 是一个 zip，内含单个条目 "data"

第 2 层（解 data）：
  k = PBKDF2(PRESHARED_64B, SALT1_32B, dkLen=32, count=10000, SHA256)
  ctr = int.from_bytes(k[16:32], 'big')
  对第 i 个 16B 块：keystream = AES-ECB.encrypt(k[:16], (ctr+i).to_bytes(16,'big'))
  明文 = 密文 XOR keystream                        → 真 zip（约 9,606 个 .mpk）
```

> 具体常量（`PRESHARED` / `SALT1` / `SALT2`）属于客户端内嵌物，本仓库**不提供**，需自行定位。
> 实测某些版本这套常量对**官方安卓版无效**（解出前两字节不是 `PK`）—— 说明不同分发渠道可能用了不同常量。

已排除的排查方向（避免重复劳动）：SALT1/SALT2 互换、迭代 1k/10k/100k、
用 GUID 字符串或 GUID 原始字节当 password、SHA256 四种直接拼接、
跳过头部 16/24/32/64/128/256 字节再解。
在 210 MB 的 `libil2cpp.so` 里搜 64 字节 PRESHARED 与两个 SALT **全部未命中** —— 不是明文硬编码。

**替代路径：从运行中的进程 dump 静态表**，不解 pack。产出约 179 个 JSON。

`.mpk` 是 **MemoryPack** 二进制序列化，**必须有 C# 类型定义才能反序列化**。
用 Python 硬解字段顺序会全错。需要 .NET 8 + 对应类型定义。

## 八、最小复现

```bash
PKG=com.example.nikke
P=/storage/emulated/0/Android/data/$PKG

# 拉七桶清单（每个几 MB）
for b in core dp fd en ja ko saus; do
  adb shell su -c "cp $P/files/com.shiftup.patch/$b/catalog.ndb /sdcard/_t && chmod 666 /sdcard/_t"
  adb pull /sdcard/_t ./${b}_catalog.ndb
done

# 拉块索引
adb shell su -c "cp $P/files/com.shiftup.patch/core/chunk/store.cdb.idx /sdcard/_t && chmod 666 /sdcard/_t"
adb pull /sdcard/_t ./core.cdb.idx

# 拉文本表（明文命名，直接 pull）
adb shell su -c "cp -r $P/files/com.shiftup.patch/saus/raw /sdcard/_raw && chmod -R 666 /sdcard/_raw"
adb pull /sdcard/_raw ./saus_raw

# 解清单 → SQLite
python nkdb_dec.py core_catalog.ndb core_catalog.sqlite

# 之后交给 fetch(bucket, key)
```

> Windows 下 adb 路径里的正斜杠会被 MSYS 改写，Git Bash 里要 `export MSYS_NO_PATHCONV=1`。
